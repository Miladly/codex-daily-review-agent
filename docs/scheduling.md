# 定时运行与补采

本项目提供命令行程序，不自动创建 Codex 桌面自动任务、launchd、cron 或系统服务。Obsidian 打开笔记库也不会触发采集。先手动成功生成一次，再在你自己的调度工具中设置周期任务。

## 调度器需要执行什么

下面是 Python 写法的调度配置示意，不是可以直接粘贴进 Shell 的命令。将所有路径替换成自己的绝对路径，避免依赖交互终端的当前目录或虚拟环境：

```python
working_directory = "/path/to/review-work"
command = [
    "/path/to/review-work/.venv/bin/python",
    "-m", "daily_review",
    "--config", "/path/to/review-work/config.local.json",
    "daily", "--through", "today", "--days", "3",
]
```

可以在 Codex 桌面自动任务中配置，或选择自己熟悉的系统调度器。示例任务说明：

> 每天在我选定的时间，用上述专用工作目录、Python 和配置执行 daily 命令。按“工作概览→分项目工作记录与产物→复盘思考→后续事项→人工补充”生成本地 Markdown、JSON 和离线计划；工作记录为主体，保留日期、原项目标识、阶段状态与证据供周报月报复用，不调用模型、不运行日志里的命令、不自动写 Notion。查看退出码、来源状态和输出路径；失败或有新稿时提醒我，内容未变且来源正常时保持安静。不要回传完整会话、数据库或私人日报正文。

若选择 23:30，需在调度器中明确它使用的时区。报告的日期边界由 `config.local.json` 中的 `timezone` 决定；两者应按你的需求对齐。本项目默认 `Asia/Shanghai`，其他用户应自行调整。配置中 `reports_dir` 改变后，调度命令无需改变。

## 运行条件

- Mac/电脑唤醒，调度环境能够运行 Python 并读写配置、私有状态和笔记目录。
- 使用 Codex 桌面自动任务时，Codex 应可运行且权限满足本地写入需求。
- SSH 来源需要该调度环境能访问的主机配置、已确认的主机密钥、非交互认证和网络；不要关闭主机密钥校验。
- 脱离交互终端运行时，环境变量、钥匙串和网络条件可能不同。先在调度器环境中试跑，不能仅凭终端成功判断定时任务一定可用。

休眠、网络、应用关闭或权限问题可能让任务延后或失败；不保证准点唤醒。Obsidian 可以关闭。

## 如何知道运行结果

查看退出码：`0` 成功，`1` 配置或运行错误，`2` 来源不完整或其他需关注情况。`state_dir/runs/last-run.json` 包含计数、来源状态与产物路径，属于私人文件。来源失败仍会保留已采集历史，不能把缺失数据当作没有工作。

每日默认回补最近三天。漏跑后手动执行同一条 `daily --through today --days 3`；更早日期用 `daily --through YYYY-MM-DD --days 1` 指定补采。反复运行会去重，不需要每天新建会话。

23:30 运行后继续工作的内容，下次仍按事件时间补回原日期。Notion 中已发布的版本不会因此自动更新，需要另行审阅并批准具体草稿。

## 格式和模型权限

默认规则运行也使用[记录与复盘融合格式](journal-format.md)，复盘区为从日志摘取的决定与问题线索。skill和格式更新不会启用每日模型调用。需要模型提炼时，可授权某几天，也可在了解摘录范围后持续授权自己的定时任务；持续授权无需每天重复确认。


## 可选的每日模型提炼

先运行 `model-preview --date YYYY-MM-DD` 检查本地输入，并确认使用已登录 Codex CLI 的模型服务处理这些有限脱敏摘录。可以只授权一次，也可明确持续授权。然后把自己的调度命令改为：

```sh
python -m daily_review daily --through today --days 3 --backend codex --model-timeout 360
```

这会实际调用模型加载内置 skill，生成工作记录和复盘；不只是让桌面助手查看采集计数。摘录仍可能含项目名称与技术内容，自动脱敏不保证移除所有自然语言隐私。最多32个会话项目组、72条当日候选及有限历史线索，摘录正文总计最多约22000字符；结构、引用ID和方法说明另外计入请求长度。不会发送完整会话、原始日志或科研文件。调度器应具备 CLI 登录、可用额度和模型出站网络；可能消耗账户额度。

相同日期、精确摘录、来源完整性、方法及指定模型未变时，复用 `state_dir/model-cache/` 中经过重新校验的结果。迟到记录或方法改变会触发重新提炼。缓存是私有数据，不可上传。

`last-run.json` 提供每日期 `backend`、`model_status`（generated/cached/fallback/disabled）、模型工作记录数，以及总 `model_calls`（适配器调用尝试数）与 `model_errors`。失败时先保存规则工作记录，返回退出码2和attention，并在正文标注模型提炼未完成；其他日期仍继续。私有错误诊断保存在 `model-failures/`，命令输出不返回摘录和错误正文。后续重跑会重试失败的日期，成功且未变化的日期不会重复调用。

不带 `--backend codex` 仍明确使用规则模式，会把所选日期渲染为规则草稿。若已启用每日模型提炼，手动补跑也应沿用完整命令，避免误将模型草稿切回规则版本。模型提炼权限不包含 Notion 发布或上传真实日报到 GitHub。


## 检查漏跑与中断

```sh
python -m daily_review status --through yesterday --backend codex
```

规则模式请省略后端参数。这个只读检查以配置时区计算昨天，核对最近完成的一轮是否覆盖该日期、是否完成要求的模型模式、笔记是否存在，以及有无尚未完成的运行。它不会读取日志或笔记正文、重跑模型、安装额外调度任务，也不能主动保证准点唤醒。需要提醒时，由你自己的调度器调用此检查并根据退出码处理。

先按[排错表](troubleshooting.md)处理错误，再用与原任务相同的完整命令补跑。不要因为看到了旧笔记就认定昨晚已成功。daily 的 stderr 提供阶段进度，stdout 保留最终 JSON；调度器可以分别保存，两个输出仍属于私人诊断材料。
